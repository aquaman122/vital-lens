# vital-lens 면접 Q&A

> 실제 구현·검증된 것만 담았다. 모든 수치와 사건은 커밋 히스토리와 NEXT.md에 근거가 있다.

## 동기와 문제 정의

**Q. 왜 만들었나? Clarity, GA 같은 도구가 이미 있는데.**

juntelecom에서 8개월 일하며 얻은 결론이 "관측 없이 만들면 폐기를 반복한다"였다. Clarity는 세션 리플레이와 히트맵은 주지만 두 가지를 안 준다: **배포 단위 회귀 비교**(이번 배포가 LCP를 얼마나 망쳤는지)와 **원시 데이터 소유**. 그 틈을 3.9KB짜리 수집기 + 내 Supabase + 대시보드로 메웠다. 핵심 화면은 release별 p75 비교 표 하나다 — 배포 전후를 나란히 놓는 것.

**Q. 성공/실패 기준은 정했나?**

PRD에 철수 기준부터 썼다. "4주간 대시보드를 주 1회도 안 열면 아카이브한다." 이전 프로젝트(compare-hub)에서 만들고 안 쓰는 도구의 비용을 배웠기 때문이다. 성공 기준은 실사용자 데이터 14일 축적과, 배포 하나의 LCP 변화가 비교 표에서 눈으로 확인되는 것.

## 아키텍처와 보안

**Q. 수집 파이프라인 구조는?**

`<script>` 한 줄(gzip 3.9KB) → Supabase RPC `vl_ingest` → 원시 `events` 테이블 → 집계 뷰/일별 롤업 → Next.js 서버 컴포넌트 대시보드. 쓰기와 읽기의 권한 경로가 완전히 분리돼 있다.

**Q. 공개된 anon 키로 수집하는데, 그 키로 데이터를 읽거나 지울 수 있지 않나?**

없다. 설계 원칙이 "**권한은 키가 아니라 함수에**"다. RLS를 전면 활성화하되 anon에게 테이블 정책을 하나도 안 만들었다 — anon 키로는 select도 insert도 직접은 불가능하다. 유일한 통로가 `security definer` RPC 하나인데, 이 함수가 사이트 존재·배치 크기(1~50)·문자열 절단·값 클램프를 검증한 뒤 insert만 한다. detail JSON은 화이트리스트 방식이라 클라이언트가 보낸 임의 키는 저장 자체가 안 된다(`__proto__` 같은 키를 넣어보는 테스트까지 통과). 읽기는 대시보드 서버의 service_role 키만.

**Q. 그 구조에서 실제로 보안 사고 날 뻔한 적은?**

있다, 그리고 그게 제일 배운 게 많은 순간이다. 정리용 함수 `vl_prune(days)`에 `revoke all ... from public`을 걸어놨는데, Supabase는 default privilege로 anon에게 EXECUTE를 따로 부여한다. `from public` 회수로는 그게 안 지워져서, **공개된 publishable 키만으로 `vl_prune(0)`을 호출해 전체 데이터를 지울 수 있는 상태**였다. 직접 호출해보다 발견했고, 역할을 명시한 revoke(`from anon, authenticated`)로 고쳤다. 이후 함수를 재생성하는 모든 마이그레이션에 권한 재명시를 규칙으로 박았다.

**Q. 대시보드는 어떻게 보호하나? Vercel Hobby면 Password Protection이 없을 텐데.**

그래서 앱 미들웨어에 HTTP Basic 인증을 직접 넣었다. 설계 포인트는 **fail closed**: `DASHBOARD_PASSWORD`가 비어 있으면 프로덕션은 503으로 아예 안 열린다. 비밀번호 비교는 상수 시간으로 하고, 사용자명이 틀려도 비밀번호 비교까지 항상 수행해 타이밍 누출을 줄였다. 배포 과정에서 env를 넣기 전 실제 프로덕션이 503을 반환하는 것으로 fail-closed가 실전 검증됐다.

## 크기 예산과 트레이드오프

**Q. 수집기 크기를 왜, 어떻게 제한했나?**

RUM 수집기가 페이지를 느리게 하면 자기모순이다. gzip 4KB를 예산으로 못 박고 `prepublishOnly` 훅에서 초과 시 발행이 실패하게 게이트를 걸었다. 현재 3918/4096B.

**Q. 예산 때문에 포기하거나 다르게 만든 것은?**

INP·LCP attribution이다. web-vitals의 `/attribution` 빌드를 쓰면 gzip 5032B로 예산 초과라 못 쓴다. 대신 기본 빌드의 `metric.entries`(PerformanceEventTiming, LargestContentfulPaint)와 resource timing에서 같은 정보를 직접 계산했다 — INP는 input delay/processing/presentation 3단계 분해에 +264B, LCP는 대상 요소 셀렉터·리소스 URL·load_delay/load_time/render_delay 분해까지 포함해 예산 안에서 해결했다.

## 측정 정확성 — 삽질에서 배운 것

**Q. 개발하면서 제일 애먹은 버그는?**

버그가 아니라 "버그처럼 보이는 정상"이었다. 자동화 브라우저로 검증하는데 LCP/FCP/CLS가 하나도 안 왔다. 인앱 브라우저 패널, Chrome 자동화 탭, CDP 강제 페인트까지 세 경로를 다 시도했는데 전부 `visibilityState: hidden`이었고 LCP 엔트리가 0개였다. 브라우저는 **화면에 실제로 보이는 페이지에만** LCP를 만든다. 결론: 이 검증은 사람이 탭을 앞에 두고 해야 하고, 역으로 이게 합성 모니터링이 못 하는 것을 RUM이 하는 이유다.

**Q. SPA 대응은?**

첫 실전 대상이 Framer 사이트였는데, Framer는 내부 이동이 전부 클라이언트 라우팅이다. 두 가지를 했다. (1) `pushState`/`popstate` 훅으로 path가 실제로 바뀔 때만 pageview를 추가 기록해 path별 트래픽을 살렸다. (2) 이 과정에서 기존 버그를 하나 찾았다 — LCP/FCP/TTFB/CLS는 탭이 숨겨지는 시점에 보고되는데, 그 사이 soft-nav가 있었으면 **엉뚱한 현재 path로 귀속**되고 있었다. 스펙상 이 메트릭들은 최초 로드에만 확정되므로 랜딩 path에 고정 귀속시키고, INP·에러·pageview만 발생 시점 path를 쓰게 분리했다.

**Q. INP·CLS가 대시보드에 비어 있는데 문제 아닌가?**

셋 다 설명 가능한 정상이다. iOS Safari(카톡 인앱 포함)는 Event Timing·Layout Shift API 미지원이라 INP/CLS/LCP를 아예 못 보낸다 — 실데이터에서 FCP 302건 vs LCP 137건의 간극이 정확히 Safari 사용자 비중이다. CLS는 layout shift가 0이면 web-vitals가 안 보내는 설계라, 계속 비어 있으면 "사이트가 안 흔들린다"는 좋은 신호다. 이런 부재의 이유를 문서에 남겨서 나중에 버그로 오독하지 않게 했다.

**Q. 전송은 어떻게 신뢰성 있게 하나?**

배치 버퍼(50건/10초) + 페이지 이탈 시 `visibilitychange`/`pagehide`에서 flush. 이탈 시에는 `sendBeacon`(헤더를 못 실어서 apikey는 쿼리로), 평시에는 `fetch keepalive`. 수집 실패는 조용히 버린다 — 관측 도구가 앱을 깨면 안 된다. 에러 수집에는 세션당 동일 message 1회 dedup을 넣어 에러 루프가 행을 쏟는 것을 막았다.

## 데이터 수명과 운영

**Q. 데이터가 무한히 쌓이면?**

3층 구조다. 원시 이벤트는 90일 뒤 pg_cron이 `vl_prune(90)`으로 삭제하고, 그 전에 일별 롤업 테이블에 p75가 멱등 upsert로 적재돼 집계는 영구 보존된다. 롤업 잡은 프룬 10분 전에 돌고, `current_date-89` 하한을 둬서 프룬으로 일부 잘린 날을 불완전한 값으로 덮지 않는다. 대시보드는 지난 날=롤업, 오늘=라이브를 합쳐 읽는다.

**Q. cron 운영에서 걸린 함정은?**

pg_cron은 UTC로 돈다. README 예시대로 `0 3 * * *`를 넣으면 KST 정오에 돈다. `0 18 * * *`(= KST 03:00)로 잡았고, 이런 함정은 전부 마이그레이션 주석과 인수인계 문서에 남겼다.

**Q. 알림 설계는? 도배 문제는 어떻게 막나?**

매시 `vl_alert_check()`가 최근 2일 release의 p75를 good 경계(LCP 2500/INP 200/CLS 0.1)와 비교해 초과 시 Discord 웹훅으로 쏜다. 도배 방지 장치가 셋: (site, release, metric) 유니크 제약으로 **평생 1회**, 샘플 8건 미만은 무시(소표본 p75는 튄다), `dev`/`unknown` release 제외. 웹훅 URL은 코드가 아니라 Vault 시크릿에서 읽어 URL이 리포에 존재하지 않는다. 전송은 pg_net 비동기라 알림이 느려도 DB에 영향이 없다.

## 실전 적용과 성과

**Q. 실제로 어디에 붙였고, 뭘 찾았나?**

kt-market(ktmarket.co.kr)에 붙였다. 여기서 측정 지점 결정이 하나 있었는데 — api.ktmarket.co.kr은 API 서버라 브라우저 페이지가 없어 CWV 자체가 존재하지 않는다. 실사용자가 있는 곳은 Framer가 서빙하는 ktmarket.co.kr이라, Framer Custom Code에 script 태그로 부착했다. 부착 몇 시간 만에 실사용자 LCP 95+샘플이 쌓였고, LCP attribution이 바로 두 건을 특정했다: 이벤트 페이지 히어로 이미지가 LCP 3402ms 중 로드에만 2126ms(이미지가 무겁다), 상품 페이지 S3 이미지가 load_delay 1755ms(발견이 늦다 — preload 부재). "느리다"가 아니라 "이 요소의 이 단계가 느리다"까지 나온다.

**Q. Framer에는 커밋 SHA가 없는데 release 비교는 어떻게?**

`data-release`를 publish마다 사람이 갱신하는 규약으로 풀었다(`framer-0827` 식). 수동이라는 한계는 있지만, 갱신 안 된 `unknown`은 알림에서 제외되게 해서 잘못된 비교로 이어지진 않는다. Vercel 배포 쪽은 커밋 SHA 7자리가 자동으로 들어간다.

**Q. 개인정보는?**

수집 안 하는 것을 명시했다: IP, UA 원문, 쿠키, 사용자 식별자 전부 없음. path는 쿼리스트링 제거, 에러 메시지 500자 절단, 세션 id는 탭 단위 랜덤 uuid라 사용자 추적이 불가능하다. 기기 정보는 mobile/tablet/desktop 분류만.

## 일반 엔지니어링

**Q. 타입은 통과하는데 런타임에 죽는 버그를 겪어봤나?**

Next.js 서버 컴포넌트가 클라이언트 컴포넌트에 `format` **함수**를 props로 넘기고 있었다. 서버→클라이언트 props는 직렬화돼야 해서 함수는 못 넘어가는데, 타입체크와 빌드는 다 통과하고 렌더에서만 500이 났다. v0.1에서 아무도 대시보드를 실행 안 해봐서 살아남은 버그다. `decimals: number`를 넘기고 포맷은 클라이언트에서 하도록 고쳤다. 교훈 둘: 직렬화 경계는 타입 시스템이 안 지켜준다는 것, 그리고 "빌드 통과"와 "실행 확인"은 다른 검증이라는 것.

**Q. 이 프로젝트에서 제일 잘한 결정 하나를 꼽으면?**

기능 추가를 멈추고 실데이터를 쌓기로 한 것. v0.2까지 만든 시점에 CLS attribution, 대시보드 필터 같은 후보가 더 있었지만, 전부 "그 데이터가 실제로 문제일 때" 착수하기로 미뤘다. 도구의 다음 우선순위는 도구가 수집한 데이터가 정해야 한다 — 철수 기준을 먼저 정한 것과 같은 원칙이다.
